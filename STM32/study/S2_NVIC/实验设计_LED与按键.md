# S2 实验设计 —— 只用 LED + 按键

> 对应 `nvic_lab.c` 的 S2 模块。原设计用 PA1 的高电平宽度 + 示波器观察 ISR 长短；
> 手上只有一颗 LED 和一个按键时，把这套实验改成**用节奏表示时间**，一样能把
> "抢占 / 排队 / 中断风暴"三件事看清楚，只是看不到纳秒级的延迟。
>
> 参考实现：`nvic_lab_led.c`（已按本工程设置编译验证：armclang V6.24 / -O1 / C99，零警告）

---

## 一、核心思路：把"时间"改成"节奏"

示波器能看"电平持续多久"，眼睛不能。但眼睛对**节奏变化**极其敏感——200ms 和 50ms 的闪烁，
一眼就能分辨；而 0.3µs 的差别本来也看不见。所以：

| | 亮 | 灭 | 次数 | 总长 | 观感 | 含义 |
|---|---|---|---|---|---|---|
| **慢闪** | 200ms | 200ms | 2 | 800ms | "嗒——嗒——"，能数清 | 低优先级 TIM3 正在执行 |
| **快闪** | 50ms | 50ms | 5 | 500ms | "哒哒哒哒哒"，像蜂鸣 | 高优先级 EXTI0 正在执行 |

TIM3 每 **1.5s** 来一次慢闪：慢闪占 0.8s，剩下 0.7s 静默。

于是整个实验只问一个问题：

> **按下按键后，快闪是"插在慢闪中间"，还是"排在慢闪后面"？**

- 插在中间 → 抢占成立（高优先级打断了低优先级）
- 排在后面 → 只能排队（子优先级相同、或抢占级比对方低）

## 二、器材与接线

- STM32F103C8T6 蓝板（板载 LED = PC13，**低电平点亮**，不用接线）
- 轻触按键 ×1、杜邦线 ×2
- ST-Link V2（下载 / 看变量）

```
        PA0 ────────┐
                    │  按键
        GND ────────┘
```

注意事项：

1. 4 脚轻触开关**同侧两脚是连通的**，要跨对角接线才算开关；接同侧等于永远短接。
2. PA0 用**内部上拉**，**不要**接 3.3V（按下会直接把 3.3V 和 GND 短起来）。
3. 如果按键已经焊在别的脚上，改 `KEY_PIN` 和 `AFIO->EXTICR[0]` 即可（PA→0、PB→1、PC→2）。

## 四、实验 0：先证明"标尺"是准的

**这一步不通过，后面全是猜。** 很多人卡在 S2，不是不懂抢占，是代码根本没跑起来。

**操作**：不碰按键，只看 LED。

**预期**：每 1.5 秒出现一组"亮200-灭200-亮200-灭200"，然后安静 0.7 秒，循环。

**验收方法**：用手机秒表数 **10 组循环 = 15 秒**（±1 秒内算对）。

### 分诊表（不通过时按顺序查）

| 现象 | 大概率原因 | 查哪里 |
|---|---|---|
| LED 完全不动 | GPIO 没配 / 时钟没开 | `GPIOC->CRH` 的 bit23:20 是不是 0x2 |
| LED 常亮或常灭，不闪 | `delay_ms` 死等（DWT 没开） | `dwt_init()` 有没有在 `main` 第一句 |
| 闪得飞快（几十 Hz） | `delay_ms` 参数被优化 / 传了 0 | 反汇编看 `delay_ms` 有没有真的读 `DWT->CYCCNT` |
| 一组闪完就再也不来了 | TIM3 中断只进了一次 | ISR 里 `TIM3->SR` 有没有清 |
| 节奏是 0.9s 不是 0.8s | `delay_ms` 有固定开销 | 正常，2×200ms 的误差来自函数调用，可忽略 |
| 按键完全没反应 | 上拉没生效 / 接线错 | 见下面"分诊 B" |

### 分诊 A：LED 一个都不亮

把 `main` 里除了 `gpio_init()` 之外全注释掉，`while(1)` 里写：

```c
GPIOC->BSRR = (1U << LED_PIN);   /* 灭 */
delay_ms(500);
GPIOC->BRR  = (1U << LED_PIN);   /* 亮 */
delay_ms(500);
```

只验证"GPIO + 延时"两件事。能闪 → 问题在 TIM3；不能闪 → 问题在 GPIO 或 DWT。

### 分诊 B：按键没反应

把 `EXTI0_IRQHandler` 整个函数体换成：

```c
EXTI->PR = (1U << KEY_PIN);          /* 写 1 清 */
GPIOC->ODR ^= (1U << LED_PIN);       /* 按一下翻一次 */
```

按一下应该"亮/灭"翻转一次。不翻 → 按顺序查：

1. `RCC->APB2ENR` 的 bit0（AFIO）开了没；
2. `GPIOA->CRL` 的 bit3:0 是不是 `0x8`（上拉输入）；
3. `GPIOA->ODR` 的 bit0 是不是 1（选上拉，不是下拉）；
4. 万用表量 PA0 对 GND，不按应为 **3.3V**，按下应为 **0V**；
5. 按键是不是接在了同侧两脚（等于常闭）。

## 五、实验 1（核心）：快闪是"插进去"还是"排在后"

**配置**：`NVIC_SetPriorityGrouping(3)`；`TIM3 = 5`（低），`EXTI0 = 0`（高）。

**操作**：盯着 LED，**在慢闪还在进行的时候**按按键（别等它闪完再按）。

**两种可能的现象**：

| | 你看到的 | 说明 |
|---|---|---|
| **A** | 慢闪走到一半，突然切成"哒哒哒哒哒"；快闪结束后，慢闪**接着**走完剩下的（不是从头再来） | ✅ 抢占成立 |
| **B** | 慢闪完整走完 2 次 → 安静 0.7s → 才开始"哒哒哒哒哒" | ❌ 没能插队 |

**判据**：不用秒表，只看**快闪的第一个"哒"出现时，慢闪数到第几次了**。
数不到 2 次 → A，抢占成立。

> 一次按不到没关系，按 5 次，只要有 1 次是"插入"的，就说明抢占成立。
> 因为窗口只占 53%（800ms / 1500ms），按在静默期里当然看不出区别。

### 为什么"接着走完"比"插进去"更值得记

A 现象里，慢闪被打断后**不是从头再来，而是从被打断的那一条指令继续**。
这正是硬件"压栈/出栈"在做事：被打断的 ISR 的 PC、寄存器全被压进栈，恢复时原样弹出。

这一点**用示波器反而看不出来**（示波器只能看到边沿），但用节奏能看出来——算是没有示波器的意外收获。

### 出现 B 时查什么

1. `NVIC_SetPriorityGrouping(3)` 是不是真的执行了、且在两个 `SetPriority` **之前**；
2. TIM3 是不是 5、EXTI0 是不是 0（别两处都设、后一处把前一处覆盖）；
3. `NVIC_EnableIRQ(EXTI0_IRQn)` 有没有执行；
4. TIM3 ISR 是不是真的在跑（如果它 800ms 内就退出了，你按在"它已经结束"的时刻，当然看不到插入）。

## 六、实验 2：把优先级对调 —— 反向验证

**只改两个数字**（分组不动，仍是 3）：

```c
NVIC_SetPriority(TIM3_IRQn,  0);    /* 现在是高 */
NVIC_SetPriority(EXTI0_IRQn, 5);    /* 现在是低 */
```

**预期**：按键 → 慢闪**一定**完整走完，才轮到快闪。

为什么：EXTI0 现在比 TIM3 低，它连"排队插队"的资格都没有，只能等——谁也不能打断正在跑的高优先级。

**这一组实验的价值**：同样的两段 ISR、同样的按键，只换了两个数字，现象完全反过来。
说明"抢占"不是代码里写出来的，是**优先级比较的结果**。

改回来：`TIM3=5, EXTI0=0`。

## 七、实验 3：改分组 —— 子优先级为什么不能抢占（Q2 的答案）

**操作**：把 `NVIC_SetPriorityGrouping(3)` 改成 `(7)`，优先级保持 `TIM3=5 / EXTI0=0`。

分组 7 = **抢占 0 位、子优先级 4 位**。此时 5 和 0 全都落在"子优先级"字段里，
谁也不能打断谁。

**预期**：和实验 1 的 B 一样——慢闪走完，快闪才来。

**一句话结论**（写进 README）：

> 只有**抢占优先级**决定"能不能插队"；**子优先级**只决定"同时排队时谁先上"。

这条用示波器也验证不出来（电平上看不出"谁先谁后"的排队顺序），用节奏刚好能看见。

## 八、实验 4：反例 —— 故意不清标志，看"中断风暴"

这是**你自己上一版踩过的坑**（当时写的是 `EXTI->PR = 0;`）。现在把它复现一遍，
让这个 bug 从"想象中的"变成"看得见的"。

**操作**：把 `EXTI0_IRQHandler` 里**两处** `EXTI->PR = (1U << KEY_PIN);` 都改成：

```c
EXTI->PR = 0;      /* ❌ 故意写错：PR 是"写 1 才清"，写 0 什么也没做 */
```

**预期**：按一下键 → LED **从此一直快闪**，慢闪再也不出现；再按按键毫无反应。

为什么：PR0 一直是 1 → ISR 一返回 NVIC 立刻又让它进来 → CPU 永远在 EXTI0 里打转，
TIM3 的 5 级中断永远排不上队，`main` 里的 `while(1)` 一次都轮不到。

**记录**：这就是"一个 ISR 霸占 CPU"的极端形态。想想看——如果这个 ISR 里还有
`printf`、浮点运算、或者等一个串口发送完成，会发生什么？（Q3 的答案就在这里）

**恢复**：改回 `EXTI->PR = (1U << KEY_PIN);`，然后按复位。

## 九、加分实验 A：清标志的位置 → 丢事件

**操作**：把 TIM3 周期改成 400ms（`tim3_init` 里 `TIM3_PERIOD_MS` 改成 `400`），
慢闪仍是 800ms（周期比 ISR 还短）。

对比两种写法：

| 清 UIF 的位置 | 现象 | 原因 |
|---|---|---|
| **进 ISR 第一件事就清**（推荐） | 慢闪**连续不断**，组与组之间没有停顿 | 800ms 结束时 UIF 早已被再次置起，返回后立刻重入 |
| **ISR 末尾才清**（你原来的写法） | 慢闪 800ms → **停 400ms** → 再慢闪 | 末尾那次清，把"ISR 期间发生的那次更新"一起清掉了 = **丢了一次中断** |

差别就是"有没有那 400ms 的静默"。这正是 Lab4 里"漏边沿"的同一个成因——
**标志要在进门时清，不是在出门时清**。

## 十、加分实验 B：用 DWT 数周期 —— 把"0.3µs"变成数字

没有示波器也能量 ISR 有多长：Cortex-M3 内核自带一个 32 位周期计数器 `DWT->CYCCNT`，
72MHz 下 **1 个数 = 13.9ns**。

代码里已经埋好了（`nvic_lab_led.c` 的 EXTI0 ISR）：

```c
uint32_t t0 = DWT->CYCCNT;
... ISR 正文 ...
g_exti_cycles = DWT->CYCCNT - t0;      /* 这一次 ISR 花了多少周期 */
```

**怎么读出来**（不用串口）：

1. Keil 里 `Debug → Start/Stop Debug Session`（Ctrl+F5）；
2. `View → Watch Windows → Watch 1`，输入 `g_exti_cycles`；
3. `View → Periodic Window Update`（勾上，不停机刷新）；
4. 按一下板上的按键 → 看数字变化。

读到的数 ÷ 72 = 微秒。参考量级：里面那 500ms 快闪 ≈ 36,000,000 周期。

**真正有用的对比**是下面这个（Q4 的量化答案）：把 ISR 里那 5 次快闪删掉，
只留"清标志 + 翻一次 LED"，再读一次 `g_exti_cycles` —— 会掉到 **几十个周期**（≈0.5µs）。
这就是 Lab4 里"边沿晚了 0.3µs"的量级来源：**ISR 越短，延迟越接近硬件下限（约 12 周期）**。

> ⚠ 别用断点看这个数：断点会让 CPU 停下来，测出来的值没有意义。
> 也不要用 Logic Analyzer —— ST-Link 没有 ETM 跟踪，那个窗口给不了实时波形。

## 十二、调参建议

嫌窗口太短、按不准？改这两个数（都在 `nvic_lab_led.c` 顶部）：

```c
#define SLOW_TIMES      3U      /* 慢闪 3 次 = 1200ms，窗口更大 */
#define TIM3_PERIOD_MS  2000U   /* 周期 2s，静默 800ms */
```

慢闪总长必须 **小于** TIM3 周期，否则会出现"ISR 没退出去、下一次中断又来了"的情况——
那属于加分实验 A 讨论的范围，会把现象搅乱。

嫌快闪不够醒目？把 `FAST_ON/FAST_OFF` 从 50 改成 30，快闪变成 ~16Hz，和 2.5Hz 的对比更强烈。
